# KPI Web Engineering Rules

## Architecture

- This repository is a self-contained Onion Architecture solution containing Domain, Application, Infrastructure, and ASP.NET Core Web projects; it must not reference projects or source files outside the repository root.
- HTTP use cases are defined in the Application layer and follow CQRS with MediatR. Controllers are thin and only bind input, dispatch requests, and return results.
- Each controller has its own file. Each command/query and its handler have separate files under `Features/<Feature>/Commands/<Operation>` or `Features/<Feature>/Queries/<Operation>`, using `<Operation>CommandHandler` and `<Operation>QueryHandler` names.
- Handlers depend on use-case repository contracts in `Application/Repositories`. Concrete repositories live in `Infrastructure/Repositories` and retain EF Core queries, business validation, access scopes, and transaction boundaries. Repository contracts return the existing Application DTOs and propagate cancellation; they do not expose EF Core or `IQueryable` to Application or Web.
- Use MediatR directly without BiUM base classes, response wrappers, or BiApp service dependencies. Technical database initialization, seeding, and maintenance remain Infrastructure services.
- The Web project must not contain Commands, Queries, or Handlers.
- Application and Infrastructure expose their own dependency-injection registration methods; Web acts only as the composition root and does not register concrete persistence services individually.
- Database access and business validation stay in the Infrastructure project. The web host does not access `KpiDbContext` from controllers or browser code.
- Public API contracts use Application DTOs or explicit request models; Domain entities are not returned directly.

## Web Experience

- Turkish is the interface language and terminology follows the established KPI product language.
- The application is a responsive working surface: primary actions and current data appear before explanatory content.
- Browser code calls same-origin `/api` endpoints through the shared API helper and presents loading, empty, success, and error states consistently.
- The static HTML shell versions its JavaScript and stylesheet URLs with the first 12 lowercase SHA-256 characters of each asset. Refresh the corresponding URL whenever that asset changes so browsers retrieve the matching interface version. Serve the HTML shell with `Cache-Control: no-cache`, including fallback routes, so navigation revalidates the current asset references.
- Navigation, dialogs, forms, tables, and notifications remain keyboard accessible and usable on mobile layouts.
- Dashboard drill-downs use visibly labeled actions and named dialogs that preserve the selected period. Evaluation lists and details reuse the authorized evaluation queries and existing record scopes; viewing another evaluator's records does not grant edit or approval access. Returning from a detail dialog preserves the list's filters.
- Dashboard evaluator cards identify active accounts with active roles through their manager role, employee-manager assignments, or persisted evaluation authorship. Promoting an assigned manager or an evaluator to administrator must not remove their card or historical evaluations. Keep evaluation statistics and drill-downs tied to the persisted evaluator user ID and selected period; authorization roles still control access independently.
- Active/passive changes are non-destructive and require confirmation when initiated as a deactivation action.
- Select controls may support single or multiple selection; multi-select filters operate on all selected values rather than only the first.
- List filters apply automatically: dropdown choices, clearing a selection, date changes, and active-state changes update results on change; text searches update while typing. Do not add an Apply/Filter button. Combine all current filter values. Paginated lists retain filter values when results refresh or pagination changes and reset pagination to the first page when a filter changes. Invalid date input/ranges must remain editable without sending an invalid query.
- Selection filters share the same normal-height dropdown component across pages and dialogs. All dropdown choices use the same circular indicator, dimensions, colors, selected state, and keyboard focus appearance as the evaluation setup controls; preserve native checkbox semantics for multiple selection and radio semantics for single selection. Clearable filters provide a reset action; required selections keep one selected value. Support keyboard/outside-click dismissal and scope each component's event cleanup to its page or dialog. Evaluation filters match stable employee, profession snapshot, and period IDs rather than display names, and preserve selections when refreshing the list.
- Form selection fields use the shared dropdown presentation while retaining their native select as the source of form values and constraint validation. Keep single/multiple values, selected defaults, option updates, form reset, and disabled/required state synchronized. Display validation errors at the visible picker and exclude presentation-only choices from form submission. Dispose observers and listeners when the form or page is replaced.
- Store supplied branding images under `wwwroot/images` and load them from local asset URLs. Preserve the original image proportions and provide accessible alternative text.
- Manual evaluation score buttons toggle an already selected score back to unanswered, preserve notes, and recalculate the summary and save eligibility. Unanswered scores remain valid only for temporary saves.
- Retired features must not remain accessible through navigation, browser routes, or HTTP controllers. Preserve existing stored data and historical migrations unless data deletion is explicitly requested; do not reuse retired permission numeric values.
- Evaluation question titles capitalize the initial letter of every word using Turkish casing in master-data reads/writes, evaluation views, and Excel exports. Preserve the remaining letters, acronyms, punctuation, and stored historical evaluation snapshots.
- KPI seed title comparisons use Turkish case-insensitive collation so capitalization changes do not create duplicate seeded questions on restart.

## API and Operations

- Async request flows propagate `CancellationToken`.
- Run temporary verification hosts on a separate port and stop them after checks. Do not leave a verification host occupying the application's Visual Studio launch-profile ports when handing the workspace back to the developer.
- Validation errors use the shared JSON problem shape and are shown to the user without leaking internal details.
- Authentication uses an HTTP-only cookie. Roles and permissions are managed as persisted data; role permissions are checked by the Application pipeline through `IAccessControlRepository` on every protected use case, while the web menu reflects the same permissions for usability.
- Browser verification of authentication or navigation changes must cover a fresh unauthenticated session and returning to the login screen after logout. Authenticated test identities alone do not verify the application startup flow.
- Active system administrators always have every defined application permission, even if stored permission rows are missing or denied. Authentication, current-user responses, authorization checks, and evaluation action flags must reflect that rule. Administrator permissions cannot be revoked through role editing; seeding and permission saves keep their stored rows allowed. Other roles continue to use their configured permissions, and inactive accounts or roles do not gain access. Permissions 9, 13, 15, and 17 are retained only for compatibility with retired page definitions, audit screens, task screens, and competency matrices; hide them from role editing and never reuse their numeric values.
- Evaluation read access does not grant edit access. Infrastructure checks record ownership for both edit queries and updates, preserves the existing administrator scope, and prevents changes to approved evaluations.
- Temporary evaluations may retain unanswered items with score 0. Permanent saves require all items to be scored 1–5 and both evaluation-create and evaluation-approve permissions; they set Approved status, approver, and approval time immediately. Evaluation status is a concurrency token so a stale draft update cannot overwrite a permanent save.
- Evaluation identity is the combination of employee, period, and evaluator user. Enforce it with a unique database index, including the legacy null-evaluator slot. Different assigned managers keep independent records; preserve legacy records without assigning them to an invented owner. Excel import checks duplicates for the authenticated evaluator; exported evaluator columns are informational and cannot impersonate another user. Dashboard employee counts remain distinct even when multiple evaluations exist.
- Starting an evaluation for a selected employee and period first checks the acting user's own record through an evaluation-create-authorized query, including for administrators. Administrators can edit other editable records explicitly from history. Resume editable records using their persisted detail IDs and original KPI snapshots, not current master-data definitions. Keep the same record open after a draft save; never silently create a replacement for an existing evaluation. Existing read/edit ownership rules also apply to resume.
- Evaluation edits carry the exact `UpdatedAt` value returned by the edit query as `ExpectedUpdatedAt` (including null before the first update). Reject stale versions before changing tracked data, and configure `UpdatedAt` as an EF concurrency token to catch overlapping writes after loading. Keep timestamps monotonic, preserve local form values on a conflict, and require an explicit reload to discard them. Browser code must forward the timestamp string unchanged to preserve database precision.
- Employee comments and acceptance are separate append-only response records. Require both history and response permissions, derive the employee from the authenticated account, and allow responses only for that employee's approved evaluations. Do not change approved scores or their approval status. Objection is not a supported response decision.
- Calibration compares only approved results within the existing history scope and never changes them or generates a combined final score. Evaluation task/reminder and competency matrix screens and their HTTP endpoints are retired; preserve existing matrix data.
- Personal goals and development plans use the existing administrator, assigned-manager, and linked-employee scopes plus a dedicated permission. Progress is explicitly entered between 0 and 100; a check-in appends its note and updates progress in the same transaction. Employee identity is immutable after creation. Version tokens protect matrix, development, and check-in updates from stale writes; archive records instead of deleting them.
- Successful tracked changes and their internal audit records are committed atomically by the Infrastructure DbContext. Record actor, entity/key, action, time, and changed field names, excluding password material; do not copy field values or secrets into audit payloads. Audit entries have no public list/update/delete API and cannot be modified/deleted through application SaveChangesAsync. Preserve historical data when retiring its screen. Technical seed SQL, bulk SQL, and direct database operations are outside this application audit mechanism.
- Cookie-authenticated API mutations require ASP.NET Core antiforgery tokens, including login and multipart imports. Expose tokens through a non-cacheable technical endpoint and send them through the shared browser API helper. Keep browser security headers centralized in Web middleware, API responses non-cacheable, production session cookies HTTPS-only, and unknown API routes distinct from the HTML fallback.
- KPI teams are the existing profession groups. A common KPI applies to everyone; a scoped KPI can target multiple professions through `kpi_criterion_profession`. Keep the legacy primary `ProfessionId` synchronized and include both legacy and linked scopes in selection and per-profession weight validation.
- The leave page only uploads Excel and lists employee leave records, with a template download and list filters/pagination. Do not expose manual create/edit/deactivate actions or a manual-save HTTP endpoint. Excel imports retain the existing view and upload (legacy manage) permissions, both enforced through MediatR; list access alone cannot upload. New permissions do not grant additional access to non-administrator roles automatically.
- Leave records retain employee, date range, leave type, notes, active state, and actor/time audit fields. Lists filter and apply deterministic ordering before database pagination. Do not infer entitlement, duration, or approval calculations from date ranges.
- Excel transfers use authorized MediatR requests and an Infrastructure repository with ClosedXML; controllers only bind multipart input or return the file. Exports apply the current filters and existing record access scopes. Imports reuse the existing save repositories, propagate the acting user, report errors by source row, and isolate each record's transaction and tracked state so a failed record cannot be saved by a later one.
- Pages supporting Excel transfer display a separate, labeled Excel action area. Keep import and template actions visible but disabled with an explanation when the user lacks management permission; enforce the same restriction on the server. The leave page offers upload and template download only; other transfer pages retain export actions.
- Excel templates use Turkish headers, an initial data sheet, usage instructions, and reference sheets. Accept only bounded `.xlsx` files with values rather than formulas. Master-data and leave imports use blank IDs for creation and existing IDs for updates, with explicit confirmation of changes including deactivation. Evaluation imports group KPI rows, skip existing employee/period/evaluator records, default to drafts, and require the normal create/approve permissions for permanent saves.
- Additional informational export columns must remain optional when reading older import templates; display-only metadata must never override the authenticated actor.
- Password changes are optional and opened explicitly from the user menu; successful login opens the requested application page without a password-change dialog or API restriction. Preserve the legacy password-change column and response fields for compatibility, but return false in current responses and do not enforce historical true values. New accounts and administrator password changes do not require a subsequent password change. Startup seeding must preserve existing accounts and passwords. Require an externally configured bootstrap secret for new production accounts and do not log initial passwords outside Development. Development login may prefill the configured bootstrap password for the default administrator through a non-cacheable environment-gated endpoint; never embed passwords in shared static assets, return them outside Development, or overwrite credentials the user has entered.
- SQL Server configuration comes from `ConnectionStrings:KpiDatabase`; environment-specific values must not be committed. An empty value enables Infrastructure-owned discovery of local default, Express, and registered named SQL Server instances using Windows authentication and shared memory. Prefer an accessible existing application database before creating one, keep instance selection deterministic, and never redirect an explicitly configured connection to another server.
- Startup applies EF migrations, packaged SQL seed scripts, and account seeding automatically, preserving existing data and passwords. Include seed scripts in both build and publish output; no manual SQL execution or EF tooling is required to run the application.
- The SQL Server engine must be running and the executing identity must have login, database creation (for first use), and schema update permissions. Do not attempt to bypass or automatically grant SQL Server permissions.
- The web host attempts database initialization at startup and retries failed initialization in the background with fresh scopes and cancellation. Keep the web shell available; until initialization succeeds, API requests return a non-cacheable 503 problem with a safe configuration message instead of accessing an incomplete schema.
- Keep EF Core runtime, SQL Server provider, and design packages on the same version. Use EF Core 10.0.2 or later in the 10.x line so design tooling does not expose NuGet BuildHost files as linked project content; keep the design package private to Infrastructure.

## Changes

- Keep changes small and feature-focused, preserve the existing stack, and do not add frontend package dependencies without a concrete need.
- Build the solution after changes. Update this file only for reusable conventions, not implementation history.
