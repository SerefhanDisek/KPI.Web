# KPI Web Engineering Rules

## Architecture

- This repository is a self-contained Onion Architecture solution containing Domain, Application, Infrastructure, and ASP.NET Core Web projects; it must not reference projects or source files outside the repository root.
- HTTP use cases are defined in the Application layer and follow CQRS with MediatR. Controllers are thin and only bind input, dispatch requests, and return results.
- Each controller has its own file. Each command/query and its handler have separate files under `Features/<Feature>/Commands/<Operation>` or `Features/<Feature>/Queries/<Operation>`, using `<Operation>CommandHandler` and `<Operation>QueryHandler` names.
- Handlers depend on use-case repository contracts in `Application/Repositories`. Concrete repositories live in `Infrastructure/Repositories` and retain EF Core queries, business validation, access scopes, and transaction boundaries. Repository contracts return the existing Application DTOs and propagate cancellation; they do not expose EF Core or `IQueryable` to Application or Web.
- Use MediatR directly without BiUM base classes, response wrappers, or BiApp service dependencies. Technical database initialization, seeding, and maintenance remain Infrastructure services.
- The Web project must not contain Commands, Queries, or Handlers.
- Application and Infrastructure expose their own dependency-injection registration methods; Web acts only as the composition root and does not register concrete persistence services individually.
- Database access and business validation stay in the Infrastructure project. The web host does not access `KpiDbContext` from controllers or browser code.
- Public API contracts use Application DTOs or explicit request models; Domain entities are not returned directly.

## Web Experience

- Turkish is the interface language and terminology follows the established KPI product language.
- The application is a responsive working surface: primary actions and current data appear before explanatory content.
- Browser code calls same-origin `/api` endpoints through the shared API helper and presents loading, empty, success, and error states consistently.
- The static HTML shell versions its JavaScript and stylesheet URLs with the first 12 lowercase SHA-256 characters of each asset. Refresh the corresponding URL whenever that asset changes so browsers retrieve the matching interface version. Serve the HTML shell with `Cache-Control: no-cache`, including fallback routes, so navigation revalidates the current asset references.
- Navigation, dialogs, forms, tables, and notifications remain keyboard accessible and usable on mobile layouts.
- Dashboard drill-downs use visibly labeled actions and named dialogs that preserve the selected period. Evaluation lists and details reuse the authorized evaluation queries and existing record scopes; viewing another evaluator's records does not grant edit or approval access. Evaluator dialogs offer separate multi-select employee and team filters derived from the authorized evaluation rows, matching employee and profession snapshot IDs and combining with the status filter. Returning from a detail dialog preserves the list's filters. Evaluator dialogs expose the shared evaluation editor only when the server CanEdit flag is true and the persisted evaluator ID equals the acting user. Use existing edit/update requests, snapshots, exact concurrency timestamps, and save permissions; approved evaluations are editable only by their author and corrections must return to draft for reapproval. Saving or cancelling returns to the evaluator list with its period and employee/team/status filters, and successful saves refresh the dashboard counts. Close and dispose the previous dialog before opening the editor; delayed form submissions must never close a replacement dialog.
- Dashboard evaluator cards identify active accounts with active roles through their manager role, employee-manager assignments, or persisted evaluation authorship. Promoting an assigned manager or an evaluator to administrator must not remove their card or historical evaluations. Keep evaluation statistics and drill-downs tied to the persisted evaluator user ID and selected period; authorization roles still control access independently.
- Dashboard manager cards and evaluator-dialog summaries show employee, approved, and pending counts without average percentages. The dialog's employee total uses the selected manager's assigned EmployeeCount, matching the card even when only some employees have evaluations; keep the visible evaluation-row count separately labeled. The dashboard summary contains only total employees, evaluated employees, and pending employees. Display combined success per employee in the combined performance ranking under the column label `Ortalama Puan`, without a standalone aggregate-percentage card. Preserve underlying score calculations and existing aggregate API contracts.
- Active/passive changes are non-destructive and require confirmation when initiated as a deactivation action.
- Master-data, user, and role management lists show only active records. Remove deactivated rows immediately while preserving current filters and the remaining order; closing the visual gap must not renumber stored display orders or alter historical evaluation snapshots.
- Per-KPI evaluation notes use full-width multiline fields with the existing 2,000-character limit. Grow and shrink them with input, size persisted content after rendering, preserve notes through score changes, and retain line breaks in detail views.
- Manager dashboard cards display active teams assigned to them, including empty teams, and any legacy teams with active assigned employees. Use the existing profession IDs and names. Record access continues through employee assignments and existing use-case permissions.
- List and dialog row actions share one pencil-triggered menu component. Keep existing actions hidden until opened and retain each page's authorization/action flags; do not add operations solely to populate a menu. Support keyboard navigation, Escape/outside dismissal, one open menu at a time, and positioning within the viewport outside table clipping. Scope listeners and cleanup to the owning page or dialog; rebind after filtering and preserve filters when returning from details.
- KPI action menus provide edit, deactivate, and permanent-delete under the existing KPI management permission. Deactivation changes only active state and update time; disable it for inactive records. Require explicit browser confirmation for deactivation and irreversible deletion, preserve current list filters, and reject deletion of any KPI referenced by an evaluation. Keep evaluation snapshots, foreign-key protection, and atomic audit records intact.
- Employee, profession, period, company-goal, user, and role menus also expose direct deactivation and permanent deletion through their existing management permissions and dedicated MediatR commands. Deactivation changes only active state and an existing update timestamp. Reject deletion of linked records instead of cascading away evaluations, employee links, manager assignments, or historical attribution; role deletion may remove its permission rows. All accounts and roles, including system roles and the acting account, follow the same permission and reference checks. End the browser session when its user or role is deactivated/deleted. Require confirmation and retain list filters after mutations.
- Authorization UI uses `Rol ve yetki yönetimi`, `Yetkileri yönet`, and `yetki` for application access permissions. Keep technical permission identifiers/API routes and employee leave terminology unchanged.
- Team-manager editors keep the manager picker, percentage input, and compact accessible X removal button on one row, including mobile layouts. Editing a valid positive percentage preserves the entered value and allocates the remainder out of 100 proportionally among every other manager; two managers use the exact complement. Distribute evenly when no previous ratios exist. Removing a row redistributes 100% proportionally across the remaining rows. Use integer hundredths and largest-remainder rounding with stable row-order tie breaks to avoid total drift; reserve at least 0.01% per remaining manager before distributing the rest, and retain incomplete/invalid input for correction without changing other fields. A single remaining manager receives 100%. Changes stay local until the existing save action; cancellation preserves persisted assignments, clearing all still requires confirmation, and server-side total/uniqueness/authorization checks remain authoritative.
- Select controls may support single or multiple selection; multi-select filters operate on all selected values rather than only the first.
- List filters apply automatically: dropdown choices, clearing a selection, date changes, and active-state changes update results on change; text searches update while typing. Do not add an Apply/Filter button. Combine all current filter values. Paginated lists retain filter values when results refresh or pagination changes and reset pagination to the first page when a filter changes. Invalid date input/ranges must remain editable without sending an invalid query.
- Selection filters share the same normal-height dropdown component across pages and dialogs. All dropdown choices use the same circular indicator, dimensions, colors, selected state, and keyboard focus appearance as the evaluation setup controls; preserve native checkbox semantics for multiple selection and radio semantics for single selection. Clearable filters provide a reset action; required selections keep one selected value. Support keyboard/outside-click dismissal and scope each component's event cleanup to its page or dialog. Evaluation filters match stable employee, profession snapshot, and period IDs rather than display names, and preserve selections when refreshing the list.
- Every shared dropdown includes a search field inside its option panel while preserving the closed summary, dimensions, and circular choice indicators. Search option labels by substring using Unicode normalization and Turkish case conversion; typing or blurring search must not change selected values, invoke list/API filters, or alter native select values. Keep selected options checked when search hides them, show a no-match status, and let clearing search reveal all options without clearing selections. Selection reset clears both the query and choices. Search supports ArrowDown to the first visible enabled choice and the existing Escape/outside dismissal. Prevent Enter in search from submitting forms, exclude search fields from form values, and synchronize search disabled state with the native select. Scope search listeners to the existing component controller and scope choice-specific CSS and disabled/reset logic to checkbox/radio inputs.
- Lists filtering distinct attributes use separate shared multi-select dropdowns instead of combined text searches. Match employees, KPIs, teams, and managers by persisted IDs; derive category choices from listed records, using the stored category value and an explicit uncategorized choice. Apply OR within each selected attribute and AND across attributes. Keep page selections in state and reapply them after edits, activation changes, deletion, navigation, and lookup refreshes; Excel exports use the resulting filtered rows. Manager filters include every assigned position and known legacy assignments. KPI profession filters include common (Herkes) records for every selected profession, alongside matching legacy and linked profession IDs; title/category filters still combine with that scope, and exports use the same visible rows.
- Form selection fields use the shared dropdown presentation while retaining their native select as the source of form values and constraint validation. Keep single/multiple values, selected defaults, option updates, form reset, and disabled/required state synchronized. Display validation errors at the visible picker and exclude presentation-only choices from form submission. Dispose observers and listeners when the form or page is replaced.
- Shared dropdown option panels use top-layer popovers so dialog/table overflow cannot clip choices. Keep panels inside their owning control in the DOM, anchor them to the summary, choose above/below based on available viewport space, constrain their size, and reposition on scroll/resize. Preserve search, selection, native form values and Escape/outside dismissal; close and dispose panels with their owning page/dialog.
- Successful permanent evaluation saves use the shared nonblocking bottom-left toast instead of a native browser confirmation. Toasts remain visible above modal dialogs, announce status through the existing live region and dismiss automatically. Retain confirmation for destructive operations and the explicit approved-edit/reapproval warning. Network failures use a clear Turkish message, preserve unsaved editor fields and permit an explicit retry; never retry a write automatically.
- Store supplied branding images under `wwwroot/images` and load them from local asset URLs. Preserve the original image proportions and provide accessible alternative text.
- Manual evaluation score buttons use the same compact 1–5 presentation in evaluation creation and the shared history/dashboard editor. Restore persisted selections, expose aria-pressed, and let Enter/Space select or clear without submitting the form. Toggle an already selected score back to unanswered, preserve notes and other items, and recalculate existing summary/save eligibility. Unanswered scores remain valid only for temporary saves; numeric legacy KPIs keep their actual-value controls and automatic scoring.
- Display evaluation totals consistently out of 100 in summaries, lists, manager dialogs, and details, using the same percentage value. Standard questions contribute (score / 5) × (100 / question count); unanswered questions contribute zero and remain in the denominator. Calculate the percentage from full-precision source scores and round only the final percentage to two decimals; do not multiply an already-rounded average. Preserve raw totals, maximums, per-question 1–5 ratings, and legacy KPI weight metadata for API/import compatibility.
- Contextual master-data creation reuses the existing editor and management permission, keeps the current page selections and unsaved input, and loads fresh editor lookups without replacing page lookup state. Only new, unsaved evaluations may receive newly created applicable KPIs; persisted evaluations retain their original question snapshots.
- The browser KPI editor exposes title, description, an optional company-goal association, common/team scope, display order, and active state. Manage the nullable company-goal link on the KPI side: one goal may have multiple KPIs and each KPI may reference one goal or none. Use the existing company-goal read permission and KPI-save request, the shared searchable single-select with a clear option, and labels that distinguish goal periods. Load goal choices alongside the existing page/contextual editor lookups without replacing unrelated page state. Offer active goals and retain any current inactive goal visibly labeled for explicit correction; existing server validation remains authoritative. Saving without a goal or clearing the association must send null. Display a linked goal name in the KPI list while preserving existing columns, filters, legacy measurement metadata, and historical evaluation snapshots. Title and description are full-width multiline textareas with the existing 1,000/2,000-character limits; reuse the shared growing-textarea behavior to wrap, grow and shrink while typing and size persisted content after opening the dialog. The KPI management list omits measurement and weight columns while preserving the underlying data and contracts. New browser-created KPIs use manual 1–5 scoring with the existing percentage result presentation and no explicit weight or target. Do not offer measurement selection or advanced metadata fields; preserve existing hidden metadata, weights, targets, and measurement settings when editing older KPIs. Keep stored data and Excel/API compatibility.
- Retired features must not remain accessible through navigation, browser routes, or HTTP controllers. Preserve existing stored data and historical migrations unless data deletion is explicitly requested; do not reuse retired permission numeric values.
- Evaluation question titles capitalize the initial letter of every word using Turkish casing in master-data reads/writes, evaluation views, and Excel exports. Preserve the remaining letters, acronyms, punctuation, and stored historical evaluation snapshots.
- KPI seed title comparisons use Turkish case-insensitive collation so capitalization changes do not create duplicate seeded questions on restart.
- KPI identity comparisons normalize Unicode, Turkish casing, whitespace, the legacy bullet character and terminal .?! punctuation, while preserving internal punctuation and exact team/common scope. Active create/update/reactivation must reject another active question with the same identity inside the existing serializable transaction. Spreadsheet matching prefers a sole active match over historical inactive copies, falling back to a unique inactive record when no active match exists; reject remaining ambiguity.
- Correct bundled duplicate questions through a separate versioned, audited Infrastructure startup cleanup after shared seeding and before database readiness, for both new and existing installations. Only consolidate active questions with matching identity and definition/measurement/validity fields; preserve different scopes or definitions. A copy may omit optional goal/category tags only when a surviving record already contains every nonempty tag; never merge conflicting tag values or overwrite metadata. Among eligible survivors keep the most-used original, then oldest creation time and ID, and deactivate extra records instead of deleting or remapping them. Preserve every evaluation/detail snapshot and score, mark cleanup atomically and do not repeat it on later startups. Keep already-applied source packages immutable.

## API and Operations

- Async request flows propagate `CancellationToken`.
- Run temporary verification hosts on a separate port and stop them after checks. Do not leave a verification host occupying the application's Visual Studio launch-profile ports when handing the workspace back to the developer.
- Validation errors use the shared JSON problem shape and are shown to the user without leaking internal details.
- Authentication uses an HTTP-only cookie. Roles and permissions are managed as persisted data; role permissions are checked by the Application pipeline through `IAccessControlRepository` on every protected use case, while the web menu reflects the same permissions for usability.
- Browser verification of authentication or navigation changes must cover a fresh unauthenticated session and returning to the login screen after logout. Authenticated test identities alone do not verify the application startup flow.
- Active system administrators always have every defined application permission, even if stored permission rows are missing or denied. Authentication, current-user responses, authorization checks, and evaluation action flags must reflect that rule. Administrator permissions cannot be revoked through role editing; seeding and permission saves keep their stored rows allowed. Other roles continue to use their configured permissions, and inactive accounts or roles do not gain access. Permissions 9, 13, 15, 17, and 18 are retained only for compatibility with retired page definitions, audit screens, task screens, competency matrices, and individual development; hide them from role editing and never reuse their numeric values.
- Authorization pages contain user accounts, role/permission management, and team-manager assignments through AuthorizationManage-authorized MediatR requests. Teams are the existing professions and support any number of distinct managers through team_manager_assignment, with positive weights of at most two decimal places totaling exactly 100%. Empty assignments explicitly clear the team. New assignments require active accounts and roles in either manager role or administrator; unchanged historical assignments may be retained when roles or active states change. Synchronize legacy FirstManagerUserId and SecondManagerUserId on the team and all its employees, including inactive employees, to the first two selected managers in one audited serializable transaction. Serialize employee membership changes with team saves; new or moved employees inherit team assignments, including additional managers through their profession, and imports join existing transactions. Every assigned manager has the existing assigned-employee scope. Preserve inconsistent legacy employee pairs until explicitly configured. Startup creates defaults only during initial bootstrap account creation; restarts preserve cleared assignments. Do not expose individual employee assignment or employee-account linking controls/endpoints. Existing employee-account links define record access. Browser user edits preserve the employee link and password; only new-user creation asks for an initial password. Users change their own password through the existing user-menu dialog. Preserve legacy user API contracts.
- Evaluation read access does not grant edit access. Infrastructure checks ownership for edit queries and updates and retains the administrator edit scope for unapproved records only. Approved records require an exact match to the persisted evaluator user ID plus the existing evaluation-create permission; administrators and approvers cannot bypass author ownership, and unknown legacy authors imply no owner. Corrections to approved records must explicitly request Draft, clear approver and approval time, preserve original question snapshots and employee-response history, and use existing concurrency checks. The browser offers a draft-save action for approved corrections and displays a success alert explaining that the record returned to draft and needs reapproval. Cancellation and failed updates must not downgrade status or display that success alert. Reapproval uses normal create/approve permissions and full scoring; combined approved results exclude corrected drafts until reapproved.
- Evaluation lists expose permanent deletion only through the server-computed CanDelete flag and explicit confirmation; evaluations have no deactivate action. Require evaluation-history access and an exact match to the persisted evaluator user ID for every status, including permanent/approved records. Administrators and approvers cannot delete another evaluator's record, and legacy null evaluators never imply ownership. Deletion does not require create/approve permission. Atomically delete the evaluation's details and employee-response records while preserving internal audit history. Status/update concurrency tokens protect deletion from overlapping changes. The main evaluation list and dashboard evaluator dialogs share the same deletion flow and server-computed ownership flag. After dialog deletion, update the dialog rows and counts and refresh the dashboard statistics while preserving the selected period and dialog employee/team/status filters. Closing the dialog during deletion must not reopen it. Viewing another evaluator's records does not grant deletion access.
- Temporary evaluations may retain unanswered items with score 0. Permanent saves require all items to be scored 1–5 and both evaluation-create and evaluation-approve permissions; they set Approved status, approver, and approval time immediately. The history action menu may finalize a complete editable draft through the approve command, requiring history/create/approve permissions and the established edit ownership/administrator scope; incomplete drafts must be completed in the editor. Evaluation status is a concurrency token so a stale draft update cannot overwrite a permanent save.
- Evaluation identity is the combination of employee, period, and evaluator user. Enforce it with a unique database index, including the legacy null-evaluator slot. Different assigned managers keep independent records; preserve legacy records without assigning them to an invented owner. Excel import checks duplicates for the authenticated evaluator; exported evaluator columns are informational and cannot impersonate another user. Dashboard employee counts remain distinct even when multiple evaluations exist.
- Starting an evaluation for a selected employee and period first checks the acting user's own record through an evaluation-create-authorized query, including for administrators. Administrators can edit other editable records explicitly from history. Resume editable records using their persisted detail IDs and original KPI snapshots, not current master-data definitions. Keep the same record open after a draft save; never silently create a replacement for an existing evaluation. Existing read/edit ownership rules also apply to resume.
- Evaluation edits carry the exact `UpdatedAt` value returned by the edit query as `ExpectedUpdatedAt` (including null before the first update). Reject stale versions before changing tracked data, and configure `UpdatedAt` as an EF concurrency token to catch overlapping writes after loading. Keep timestamps monotonic, preserve local form values on a conflict, and require an explicit reload to discard them. Browser code must forward the timestamp string unchanged to preserve database precision.
- Employee comments and acceptance are separate append-only response records. Require both history and response permissions, derive the employee from the authenticated account, and allow responses only for that employee's approved evaluations. Do not change approved scores or their approval status. Objection is not a supported response decision.
- The approved-manager comparison page is labeled `Onaylı Amir Sonuçları` in navigation, page titles, and permission descriptions. Show individual approved scores and the combined percentage per employee/period, labeling the result Ortalama Puan consistently in the comparison screen and its spreadsheet reports. Combined percentage is the sum of each currently configured team manager's individual percentage multiplied by their weight, rounded to two decimals. Use the evaluation's profession snapshot ID to resolve the current team configuration; weight changes apply to existing results immediately without changing individual scores or evaluation snapshots. Match managers by persisted evaluator user ID, never roles, names, historical positions, or record order. Require exactly one approved evaluation per configured manager, matching profession snapshots within the employee/period group, and a valid 100% configuration. Missing/draft records, unknown authors, and unconfigured former managers never supply an invented score or normalized replacement; retain their individual results and explain pending or unconfigured results. Dashboard combined rankings and averages use the same server calculation over authorized rows and average only complete results. Preserve historical evaluator position snapshots as attribution, allow positions above two for new records, and leave unknown legacy authors unclassified.
- Evaluation task/reminder, competency matrix, and individual development/goal/check-in screens and their HTTP endpoints are retired. The application focuses on period evaluations. Preserve existing stored matrix/development data, relationships, and migrations.
- Successful tracked changes and their internal audit records are committed atomically by the Infrastructure DbContext. Record actor, entity/key, action, time, and changed field names, excluding password material; do not copy field values or secrets into audit payloads. Audit entries have no public list/update/delete API and cannot be modified/deleted through application SaveChangesAsync. Preserve historical data when retiring its screen. Technical seed SQL, bulk SQL, and direct database operations are outside this application audit mechanism.
- Cookie-authenticated API mutations require ASP.NET Core antiforgery tokens, including login and multipart imports. Expose tokens through a non-cacheable technical endpoint and send them through the shared browser API helper. Keep browser security headers centralized in Web middleware, API responses non-cacheable, production session cookies HTTPS-only, and unknown API routes distinct from the HTML fallback.
- KPI teams are the existing profession groups. A common KPI applies to everyone; a scoped KPI can target multiple professions through `kpi_criterion_profession`. Keep the legacy primary `ProfessionId` synchronized and include both legacy and linked scopes in selection and per-profession weight validation.
- The leave page only uploads Excel and lists employee leave records, with a template download and list filters/pagination. Do not expose manual create/edit/deactivate actions or a manual-save HTTP endpoint. Excel imports retain the existing view and upload (legacy manage) permissions, both enforced through MediatR; list access alone cannot upload. New permissions do not grant additional access to non-administrator roles automatically.
- Leave balance imports and their upload-template download require both existing LeaveView and LeaveManage permissions through MediatR; viewing balance lists requires LeaveView. Keep the UI upload-only without a manual balance-save endpoint.
- Leave balance snapshots store the supplied remaining days and entitlement date in a separate employee-linked model with actor/time auditing; preserve historical date-range leave records and their existing contracts. The leave screen lists uploaded balances with employee/team filters, an inclusive entitlement-date range, deterministic database ordering, and database pagination. Fractional and negative supplied balances are valid. Never infer entitlement, accrual, duration, approval, or business-day calculations from dates. Resolve one active employee by full name; when none exists and no inactive employee has that name, create active personnel through the employee repository using the shared Meslek atanmadı profession, creating that profession through the profession repository when absent. Reject ambiguous active names and require explicit reactivation of existing inactive personnel rather than creating replacements.
- Excel transfers use authorized MediatR requests and an Infrastructure repository with ClosedXML; controllers only bind multipart input or return the file. Exports apply the current filters and existing record access scopes. Imports reuse the existing save repositories, propagate the acting user, report errors by source row, and isolate each record's transaction and tracked state so a failed record cannot be saved by a later one.
- Employee/leave imports may create related personnel and professions within their existing resource-specific import permissions; do not grant additional role permissions or create sign-in accounts, credentials, or employee/account links. Resolve names, save related records, and save the source row inside the existing serializable row transaction through the established employee/profession/leave repositories. Roll back all related data and audit entries on row failure and clear tracked state before processing the next row.
- Pages supporting Excel transfer display a separate, labeled Excel action area. Keep import and template actions visible but disabled with an explanation when the user lacks management permission; enforce the same restriction on the server. The leave page offers upload and template download only; read-only comparison reports offer export and a blank template without import; other transfer pages retain export actions.
- Excel templates use Turkish headers, an initial data sheet, usage instructions, and reference sheets. Accept only bounded `.xlsx` files with values rather than formulas. Legacy KPI and date-range leave imports use blank IDs for creation and existing IDs for updates, with explicit confirmation of changes including deactivation. Employee exports and templates contain exactly Ad Soyad, Meslek, and Aktiflik durumu; their profession reference sheet contains names without IDs. Name-based employee imports match full names across active and inactive records and update the same employee when unique. A supplied profession may disambiguate an existing duplicate name only when it identifies exactly one record. Apply a supplied profession to the matched employee, create the profession through the existing profession repository when its name is absent, and reject inactive or ambiguous profession matches without silently reactivating them. Meslek values and the Meslek column are optional: preserve the matched employee's profession when omitted, and use the shared Meslek atanmadı profession for new personnel. Create unmatched employees through the existing employee save repository; reject ambiguous database matches and repeated file full names, including conflicting professions. Renames require the editor or legacy ID-based input. Preserve boolean Evet/Hayır parsing, the blank-true default, historical evaluation links and unchanged manager assignments; new or moved employees inherit destination team assignments. Match and save inside the existing serializable row transaction and preserve legacy five-column employee imports. Evaluation exports and templates contain exactly Çalışan, Ekip, Dönem, Not, KPI, Puan, Amir Görüşü, and Değerlendiren Amir in that order. Write one KPI per row with its original 1–5 rating; omit technical IDs, transfer groups, dates, actual values, and hidden evaluation metadata from new files. Name-based imports group employee/team/period/evaluator-label rows, resolve a unique active employee/team pair, active period, and applicable current KPI title, and reject ambiguous names instead of selecting a match. KPI title matching follows Turkish case rules. Shared manager feedback must agree across a group; per-question notes remain separate. Değerlendiren Amir is informational/grouping metadata and never overrides the authenticated actor. Skip existing employee/period/evaluator records and default to drafts; permanent imports retain normal create/approve permissions. Never infer actual metric values missing from simplified files. Keep legacy ID-based templates readable and preserve existing data.
- KPI Excel exports and templates contain exactly KPI, Açıklama, Ekipler, Herkes, Kategori, and Bağlı olduğu şirket Hedefi, with name-only team/goal references and wrapped multiline text cells. New imports resolve active team names separated by semicolons and an optional unique active company-goal name. Herkes=Evet applies to all teams and ignores listed teams, matching the existing save behavior. Match Turkish-normalized KPI titles plus the exact set of legacy/linked team IDs, including inactive KPI records; update only supplied text/category/goal fields, preserve omitted measurement/target/weight/order/active/validity/SMART metadata, and create unmatched records with the standard manual 1–5 defaults, order 1, weight 0, and active state. Reject ambiguous matches and repeated file identities regardless of team order or equivalent boolean spellings. Title/scope changes require the editor or explicit legacy ID input. Reuse the KPI save repository in the serializable row transaction with existing audits and error isolation. Preserve legacy 25-column KPI imports.
- Keep one current leave balance per employee, enforced by a unique employee index. Reimport updates the supplied days and date, preserves creation metadata, records the updater, and leaves employees absent from the file unchanged. Reject repeated employee names within a file. Resolve and save each balance inside the existing serializable row transaction; route writes through the leave repository, retaining atomic auditing and failed-row isolation.
- Leave balance Excel templates and exports contain exactly Adı Soyadı, Kalan İzin Gün Sayısı, and İzin Hak Ediş Tarihi. Employee references contain names without IDs. Read the first worksheet regardless of its name, locate the first content row as the header after leading blank rows, and preserve original row numbers in errors. Support native Excel dates and existing textual date formats, numeric or comma/point fractional and negative days, and the normal file/formula limits. Keep legacy ID-based date-range imports readable without converting them into balances.
- Approved-manager comparison exports require both CalibrationView and EvaluationHistory through the existing spreadsheet MediatR query. Reuse authorized evaluation history and the shared ApprovedManagerResults calculation; apply every selected period ID, with an empty selection meaning all authorized periods. Exports and blank templates share exactly five data columns: Çalışan, Ekip, Dönem, Amir Sonuçları, and Ortalama Puan. Write one row per employee/period, put every authorized manager result and its current weight in the multiline manager-results cell, and keep combined scores numeric. Omit technical IDs, difference, result status, and additional manager-detail sheets. The comparison screen also omits the difference column while preserving existing API contracts and score calculations. Leave incomplete combined scores blank rather than inventing zero values. Include report-specific instructions and retain existing Excel styles, cancellation, and row limits. Template download uses the same comparison/history permissions and returns headers without data; comparison reports do not support import.
- Additional informational export columns must remain optional when reading older import templates; display-only metadata must never override the authenticated actor.
- Password changes are optional and opened explicitly from the user menu; successful login opens the requested application page without a password-change dialog or API restriction. Preserve the legacy password-change column and response fields for compatibility, but return false in current responses and do not enforce historical true values. New accounts and administrator password changes do not require a subsequent password change. Startup seeding must preserve existing accounts and passwords. Require an externally configured bootstrap secret for new production accounts and do not log initial passwords outside Development. Development login may prefill the configured bootstrap password for the default administrator through a non-cacheable environment-gated endpoint; never embed passwords in shared static assets, return them outside Development, or overwrite credentials the user has entered.
- SQL Server configuration comes from `ConnectionStrings:KpiDatabase`; environment-specific values must not be committed. An empty value enables Infrastructure-owned discovery of local default, Express, and registered named SQL Server instances using Windows authentication and shared memory. Prefer an accessible existing application database before creating one, keep instance selection deterministic, and never redirect an explicitly configured connection to another server.
- Startup applies EF migrations and repeatable SQL normalization, bootstraps security, then imports the versioned shared-data package through Infrastructure services. Include seed SQL and JSON in both build and publish output under Database, outside wwwroot; no backup restore, manual SQL execution or EF tooling is required at runtime.
- Shared-data packages are additive, versioned snapshots with source-to-target ID mapping in dependency order. Existing target records, passwords, permissions, inactive states, team assignments and leave balances take precedence; process sources in declared priority order. Match stable business identities instead of numeric IDs, use Turkish-normalized names and exact KPI team scopes, and disambiguate historical duplicate KPIs by their original creation time. Reject unresolved ambiguity and commit records, audits and the version marker in one serializable transaction. Preserve evaluation snapshots and historical audit payloads. Packages exclude passwords/hashes; new accounts use the existing environment-sensitive bootstrap-secret policy. Only a database identified as newly created before migration may restore packaged public bootstrap account/role metadata; never apply that exception to an existing installation.
